## 难点 1：相册多选批量识别（≤5 张逐张串行 + 清单确认 + 新物种生成）

| 项 | 值 |
|---|---|
| 日期 | 2026-08-16 |
| 分类 | 数据 / 交互 / 依赖限制 |
| 难度 | 高 |
| 状态 | 已实施（2026-08-16 实施完成） |
| 涉及模块 | `pages/recognize`、`pages/index`、`utils/util.js`、`recognizeFlower`、`requestFlowerGenerate`、`generateFlowerWorker` |
| 关联记录 | [修复与优化记录](修复与优化记录.md)「批次 2026-08-16：相册多选批量识别设计定稿」 |

### 1. 原有技术实现

- 选图：`util.chooseOneImage` 用 `wx.chooseMedia` `count: 1`，一次只能选 **1 张**；
- 识别：单图 `phase: idle → recognizing → result → success`，`candidates` 为单张图的 Top3 候选、`selectedIndex` 单选、`confirmSave` 只入库一张；
- 识别链路上限：每日 **20 次**（`RECOGNIZE_DAILY_LIMIT` 云函数事务强制）、云函数 **20s 超时**、单张约 3~5s、图片最长边 ≤1080 质量 75、MD5 同图去重不扣次数；
- 未收录花生成：单图触发「收录并生成花卡」→ `requestFlowerGenerate` 建任务 → `pollGenTask` 轮询（4s×45 次≈3 分钟）→ `attachSpecies` 挂花种；`genIndex` 保证同一时间只 1 个生成任务；worker **每 2 分钟只处理 1 个**任务、每日生成上限 **3 次**。

### 2. 当前要实现的功能

从相册**多选**（单次 ≤5 张）一次性识别多张：逐张串行识别 → 批量统一清单确认；失败单张跳过标记、最后统一处理；中途退出保留已识别结果；并兼容**未收录花（新物种）**的批量生成与收录。

### 3. 实现方案与原因

**核心约束推导（决定方案形态）**：

1. **必须逐张串行**：`recognizeFlower` 云函数超时 20s，单张约 3~5s，一次调用处理多张必超时——所以批量 = 前端逐张循环调 `recognizeFlower`，每张独立上传/识别，进度「3/5」；
2. **选图按剩余次数截断**：批量 N 张消耗 N 次每日配额，选图时 `min(选中数, 剩余次数)`，超出提示并截断；
3. **统一清单确认（方案 B）**：多张结果集中在 `batch_result` 阶段逐张确认，每张默认第一个命中候选、可展开切换 Top3 / 手动纠正；「确认全部入库」逐张 `saveCard(create)` 汇总；
4. **新物种批量生成的关键取舍**：
   - worker 每 2 分钟只处理 1 个任务 → 多张未收录花必须**串行排队**，且**生成完成前该张不可确认入库**（无 species 无法入库）；
   - 每日生成上限 3 次 → 生成前**前置配额提示**（`GEN_LIMITED` 兜底）；
   - 队列长耗时 → 明确提示「按序生成，完成后图鉴可查」，中途退出后台继续（worker 处理，任务不丢）；
5. **数据模型**：单图 `candidates` 扩展为多图 `batchList`（每项含 `tempPath/fileID/status/candidates/selectedIndex/confirmed/genState/speciesId`），新增 `phase: 'batch'`（识别中）与 `'batch_result'`（清单确认），单图路径保留兼容。

**详细设计见** [批量识别方案](批量识别方案.md)。

### 4. 实施反馈与结论（结果）

- **实施结果（2026-08-16）**：已落地——`util.chooseMultiImages` 多选、`runBatchRecognize` 逐张串行、`batch_result` 清单确认（展开切换候选/失败重试/存相册/确认全部入库汇总）、批量未收录花生成（串行锁 + `GEN_LIMITED` 配额提示 + 生成中置灰）、首页相册入口改多选；单图路径保留兼容（`onLoad` 按 tempPath/tempPaths 分发）；
- **验证**：`node --check` 通过；批量核心逻辑测试 10 项 `ALL PASS`（初始化占位、成功/失败/重复/未收录各态、确认过滤、汇总计数）；
- **待真机验证**：批量耗时（5 张约 15~25s）、生成排队体验、中途退出保留已识别、单图路径回归；
- **遗留待复盘**：批量中 MD5 重复图自动跳过（不弹窗）的交互细节、生成中张与「确认全部入库」的并发边界、失败张「换一张重试」当前复用单图识别流程的体验。

## 难点 2：批量入库被未收录花生成阻塞（已收录花照片未入库）+ Seedream 敏感词失败重试

| 项 | 值 |
|---|---|
| 日期 | 2026-08-17 |
| 分类 | 交互 / 依赖限制 |
| 难度 | 高 |
| 状态 | 已解决（2026-08-17 修复） |
| 涉及模块 | `pages/recognize/recognize.js`（processBatchInOrder）、`generateFlowerWorker`（generateImage） |
| 关联记录 | [修复与优化记录](修复与优化记录.md)「批次 2026-08-17：批量入库阻塞修复 + Seedream 敏感词失败优化」 |

### 1. 原有技术实现

- 批量确认入库 `processBatchInOrder`：**严格串行**——按 batchList 顺序逐张处理，未收录花 `await pollBatchGenTask`（每 4s 轮询、最多 45 次约 3 分钟）阻塞循环，直到该张生成+入库完成才处理下一张；
- `generateFlowerWorker` 生图失败：`generateImage` 抛普通 `Error('Seedream 未返回图片: ...')`，worker 当**普通失败**进入重试队列（每 2 分钟重试 1 次、最多 3 次后 failed 退配额）；
- 页面退出：`onUnload` 只 `stopGenPolling` 清轮询定时器。

### 2. 当前要实现的功能

修复两个真机问题：① 批量上传「已收录花+未收录花」时，未收录花生成慢/失败**不应阻塞已收录花入库**（否则照片丢失）；② 未收录花名触发 Seedream 生图平台敏感检测时，**不应反复重试让用户干等**，应快速失败并明确提示。

### 3. 实现方案与原因

**问题现场**（用户反馈 + worker 日志）：
- 上传「罂粟花+月季花」批量识别：罂粟（未收录）先生成，日志 `InputTextSensitiveContentDetected`（罂粟花名触发 Seedream 生图平台**输入敏感检测**）→ worker 每 2 分钟重试 1 次、最多 3 次 ≈ 6+ 分钟；
- 月季（已收录）排在罂粟后，被串行循环 `await` 卡住；用户等罂粟时退出页面 → `onUnload` 清轮询 → promise 悬挂 → 月季 `saveBatchItem` 从未执行 → **图鉴月季卡照片未入库**。

**修复设计（两处）**：

1. **前端两阶段入库**（`processBatchInOrder` 重构）：
   - 阶段一按原顺序：已收录花**立即 `saveBatchItem` 入库**（秒级，不等待生成）；未收录花只 `requestFlowerGenerate` 建任务入 `genQueue`（不阻塞）；
   - 阶段二：已收录全部入库后再**串行轮询**未收录生成队列（每张生成完成自动入库）。
   - 原因：已收录花入库不依赖生成，让用户等未收录（慢/可能失败）是错误取舍；两阶段兼顾「按序处理」观感与「不阻塞」可靠性。
2. **worker 敏感错误快速失败**（`generateImage` + catch）：
   - `generateImage` 解析平台错误：`InputTextSensitiveContentDetected` → 抛 `code: 'SEEDREAM_SENSITIVE'` + 文案「该花名未通过生图平台内容检测，无法生成花卡」；
   - catch 把 `SEEDREAM_SENSITIVE` 纳入 `isUnsafe`：**立即 failed、不重试、不退配额**。
   - 原因：外部内容策略拒绝是**确定性失败**，重试必然再次撞墙，只会浪费用户时间与 worker 周期。

### 4. 实施反馈与结论（结果）

- **已解决（2026-08-17）**：前端两阶段入库 + worker 敏感错误快速失败均已落地；
- **验证**：`node --check` 通过；两阶段逻辑测试 5 项 `ALL PASS`（已收录先入库不阻塞、未收录入队、串行生成、罂粟失败不影响月季）；
- **需真机验证**：批量混花入库（未收录卡住时已收录照片正常入库）、罂粟花快速失败提示；
- **遗留待复盘**：未收录花生成失败后用户重新识别会再次触发生成（failed 任务可重建，再次撞敏感墙）——当前靠用户换花名/放弃，是否要加「失败花名本地记忆不再生成」待定；
- **教训**：**串行 await 长耗时/可能失败的外部操作时，务必考虑对后续步骤的阻塞**；外部平台策略性错误应识别并快速失败，而非盲目重试。

## 难点 3：识花时间线「节点内滚动 + 边界滑动切换节点」的手势分层

| 项 | 值 |
|---|---|
| 日期 | 2026-08-17 |
| 分类 | 交互 |
| 难度 | 中 |
| 状态 | 已解决（2026-08-17 实施） |
| 涉及模块 | `pages/index/index.js`、`index.wxml`、`index.wxss`（识花时间线） |
| 关联记录 | [修复与优化记录](修复与优化记录.md)「批次 2026-08-17：识花时间线节点内滚动 + 边界滑动手势切换节点」 |

### 1. 原有技术实现

- 识花时间线：左侧时间轴 + 右侧 `swiper`（`vertical` 纵向），每个 swiper-item 是一个「整点小时」时间节点；
- 节点内记录曾用**普通 view 布局**（不滚动）：上下滑动手势全部交给 swiper 切换节点，节点内记录多时超出 slide 高度被裁剪（`overflow: hidden`）——用户看不到该节点全部识花；
- 切换方式：swiper 手势上下滑（后来改为 `onTimelineTap` 点击时间轴 + 边界事件）。

### 2. 当前要实现的功能

① 节点内记录**可上下滑动**展示该节点全部识花；② 节点内滚到顶部/底部后**继续滑动即切换相邻时间节点**（连续浏览，不打断手感）。

### 3. 实现方案与原因

**核心矛盾**：同一块触摸区域上，纵向手势既要「滚节点内内容」又要「切节点」——两个滚动容器抢手势。

**方案：swiper `disable-touch` + 节点内 scroll-view 接管手势 + 边界事件联动**：

1. `swiper` 加 **`disable-touch`**：禁用 swiper 自身触摸手势（swiper 只保留 `current` 属性驱动切换动画），触摸全部交给节点内 scroll-view；
2. 节点内记录改 `<scroll-view scroll-y>`，绑定 `bindscrolltoupper`/`bindscrolltolower`：
   - 滚到顶部 → `onTimelineScrollToUpper`：切到上一节点，上一节点 `scroll-top` 置 99999（滚到底部，「从下面接上」的连续感）；
   - 滚到底部 → `onTimelineScrollToLower`：切到下一节点，新节点从顶部开始；
3. **防抖**：`_timelineSwitching` 标记（300ms）——切换后 scroll-top 被 setData 设置会触发 `scrolltoupper`，若不加锁会**立刻跳回上一节点**；
4. 高度约束：`.timeline-records` 用 `flex:1; height:0`（flex column 父容器下收缩），保证 scroll-view 高度 = 剩余空间、不撑爆 swiper-item；
5. `scroll-top` 按节点存 `timelineScrollTops` 数组（每个节点独立位置），`99999` 表示「滚到底部」，scroll-view 自动滚到内容末尾。

**为什么不直接用 swiper 手势切换**：swiper 纵向手势会与节点内 scroll-view 抢滚动（swiper 优先接管），节点内内容将无法滚动——必须禁用 swiper 手势、由 scroll-view 全权接管，再用边界事件「代发」切换指令。

### 4. 实施反馈与结论（结果）

- **已实施（2026-08-17）**：节点内 scroll-view 滚动 + 上下边界联动切换 + 防抖均落地；
- **验证**：`node --check` 通过；滚动边界逻辑测试 7 项 `ALL PASS`（下切/上切、新节点滚到底/顶、首尾边界不切换、防抖忽略）；
- **需真机验证**：手势手感（节点内滚动与边界切换的衔接是否顺滑）、单节点记录少时边界事件是否误触发；
- **边界情况**：单节点记录不足一屏时，上滑到头/下滑到底为同一位置，`scrolltoupper`/`scrolltolower` 不会因内容不满而误切（scroll-view 内容不超出一屏时边界事件不触发）；
- **教训**：**多个纵向滚动容器同区互斥时，禁用外层容器手势 + 内层全权接管 + 边界事件转发切换，是比「手势拦截/阈值判断」更可控的方案**；切换类副作用务必加防抖，防止状态设置反噬触发自身事件。
### 5. 修改记录（2026-08-17：切换自激振荡修复）

**触发原因（Bug 现场）**：滑动时间线时界面快速抖动、时间节点不停切换，**即使没有触摸也持续抖动**。

**产生 bug 的原因**：
- 切换防抖时间窗过短（**300ms**），而 `scroll-top` 受控绑定 + swiper 切换动画 + 边界事件的完整触发周期**超过了 300ms**；
- 原方案为「从下面接上」设置 `scroll-top=99999`（滚到底），切换后新节点 scroll-view 被强制滚动到边界 → 又触发反向 `scrolltoupper/lower` → 防抖一过再次切换 → 形成 **A→B→A→B 往复自激振荡**；
- 且无**方向识别**——往返切换方向交替，原单一时钟防抖无法区分「用户真实连续滚动」与「状态设置引发的边界事件」。

**原考虑的不足**：
- 只用了**单一时间窗防抖**（`_timelineSwitching` 300ms），未考虑 scroll-view 受控滚动的边界事件**会自我触发**（副作用反噬），也未识别切换方向；
- `scroll-top=99999` 的「滚到底接续」设计过度——它制造了强边界触发，而非只在用户真实滑动时触发。

**怎么解决的**：
- 移除 `99999` 反向滚底跳转（新节点统一从顶部开始），从源头消除 `scroll-top` 设置的强触发；
- 新增 **`canTimelineSwitch(dir)` / `lockTimelineSwitch(dir)`**：
  - 切换锁时间窗 300ms → **800ms**（覆盖 swiper 动画 + scroll-top 设置 + 边界事件全周期）；
  - **方向锁**：同一方向 800ms 内连续触发视为振荡并忽略（`_timelineLastDir` / `_timelineLastDirAt`）——打破往返弹跳；
- 点击时间轴统一走 `lockTimelineSwitch(0)`（dir=0 不匹配任何方向，不误判振荡）。

**现在修复情况**：
- `node --check` 通过；振荡拦截逻辑测试 7 项 `ALL PASS`（锁复位后可切换、同方向连续触发被拦、时间锁+方向锁叠加、反向不受影响、点击不误判）；
- 关联修复记录：「批次 2026-08-17：识花时间线切换自激振荡修复」；
- 待真机复核：滑动不再抖动、节点切换正常、无触摸时界面静止。

**经验沉淀**：**受控滚动（scroll-top）切换类逻辑，必须用「时间窗 + 方向识别」双重防抖**，并避免用「跳转边界值」制造强触发；状态设置引发的边界事件要与用户真实滚动区分。
