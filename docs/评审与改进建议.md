## 一、🔴 高危：建议上线前处理

### 1.1 `addPhoto` 追加照片绕过内容安全检测

- **位置**：`cloudfunctions/saveCard/index.js` 的 `addPhoto`/`create` 分支；检测只在 `recognizeFlower/index.js` 中。
- **问题**：用户识别入库后，可在详情页持续追加照片（`miniprogram/pages/detail/detail.js` `addPhoto`），**这条链路上传的图片不经过 `imgSecCheck`**。识别时检测过一次，不代表后续追加安全；违规图片可借此进入云存储。
- **建议**：方案 A——`saveCard` 的 create/addPhoto 分支复用内容安全检测逻辑（与 recognizeFlower 相同的 jpeg/png 重试与 87014 判定）；方案 B——把「上传后检测」收敛到独立云函数（如 `uploadPhoto`）统一出口，识别与追加都走它。若采用 A，注意图片仍需 ≤1M，前端压缩逻辑已满足。

### 1.2 删除数据不清理云存储文件（孤儿文件 + 隐私承诺未兑现）

- **位置**：`saveCard/index.js` `deletePhoto`/`deleteCard` 只删数据库记录；`recognize` 页识别失败/未入库的照片也不清理。
- **问题**：隐私政策承诺「如需删除全部个人数据，可在小程序内删除对应花卡」，但云存储 `user-photos/` 里的原图永远留存。既占存储（免费额度会满），也与隐私承诺不符。
- **建议**：
  1. `deletePhoto`/`deleteCard` 在删库前调用 `cloud.deleteFile({ fileList })` 删除对应 fileID；
  2. 识别失败/未确认入库时，前端 `finally` 或服务端兜底删除已上传的 fileID（可加「识别失败自动清理」）；
  3. 配置云开发「存储生命周期」策略或定时触发器兜底清理孤儿文件。

### 1.3 账号注销能力缺失

- **位置**：`miniprogram/pages/profile/profile.wxml` 隐私政策第 5 条「账号注销能力后续提供」。
- **问题**：微信平台对收集用户信息的小程序要求提供注销/删除数据能力，且这是隐私承诺。当前没有任何注销入口。
- **建议**：我的页增加「注销账号」入口 → 二次确认 → 删除该 openid 下全部 `user_cards` + `rate_limits` 记录 + 云存储照片 → 提示完成。这是纯服务端操作，实现成本低，建议 P1 排期。

### 1.4 云存储权限需确认「仅创建者可读写」

- **位置**：`miniprogram/utils/util.js` 上传路径 `user-photos/`；README「数据与合规」声称「用户照片存云存储私有目录，仅本人可见」。
- **问题**：微信云开发**云存储默认权限是「所有用户可读，仅创建者可写」**——如果不手动改，fileID 一旦泄露（如通过收藏/分享间接暴露）照片可被任何人读。fileID 形如 `cloud://...` 的 URL 本身就含在数据库文档中下发给前端。
- **建议**：部署清单中加一条硬性检查：云开发控制台 → 存储 → 权限设置 → 改为「仅创建者可读写」；并在 README/技术文档的部署步骤里标注为**必改项**。

### 1.5 云函数层缺少输入长度校验

- **位置**：`saveCard/index.js` 的 `updateNote`（`event.note`）、`updateLocation`、`makePhoto` 的 note/location 直接入库。
- **问题**：前端 textarea 有 `maxlength=200`，但云函数可被任意调用方（抓包/直接 callFunction）绕过——可写入超大字段甚至超 16MB 文档上限导致写入失败或存储膨胀。
- **建议**：云函数对 `note`（如 ≤200 字符）、`location`（如 ≤100 字符）、`photoFileID` 格式做长度与类型校验，超限返回 `BAD_PARAM`。

## 二、🟠 中危：功能缺陷与体验问题（已全部修复）

### 2.1 识别失败也扣限流次数

- **位置**：`recognizeFlower/index.js` 第 1 步就 `consumeRateLimit`，后续下载失败/内容安全拒绝/百度报错均不退还。
- **问题**：非用户过错（服务端超时、百度 5xx、误判不合规）也消耗当日 20 次配额，体验不佳。
- **建议**：区分「可退次数」：下载失败、百度服务错误、安全检测接口异常（fail-open 前）等**服务端原因**退还次数；「识别成功但没匹配上」属正常消耗。简单做法：在失败分支调 `_.inc(-1)`（下限 0）。

### 2.2 限流存在并发竞态（TOCTOU）

- **位置**：`consumeRateLimit`（recognizeFlower/index.js）先 `get` 再 `update/set`，非原子。
- **问题**：同一用户并发两次请求，可能都读到 count=19 通过检查，最终超限 1 次。云函数默认单实例顺序执行可缓解，但并发调用时仍可能发生。
- **建议**：用 `db.runTransaction` 做「读计数 → 校验 → 自增」；或先 `update inc(1)` 再读回校验（超过限额则 `inc(-1)` 并拒绝）。成本低，建议顺手改。

### 2.3 徽章数量文档不一致（README 说 8 枚，代码 9 枚）

- **位置**：`README.md` 与 `pages/achievements/achievements.js` 注释写「8 枚」，实际 `getAchievements/index.js` 的 `BADGES` 数组是 **9 枚**（多一枚 `first_legendary` 一见倾心）。
- **问题**：文档误导；成就页若做过 UI 排布假设（如 8 宫格）也可能受影响。
- **建议**：README 与页面注释改为「9 枚」，或将徽章定义抽到共享配置（见 2.5）。

### 2.4 「我的」页限流文案硬编码

- **位置**：`miniprogram/pages/profile/profile.wxml` 第 29 行「每人每日最多识别 {{20}} 次」硬编码 20。
- **问题**：若调整 `config.RECOGNIZE_DAILY_LIMIT` 或云函数环境变量，文案与实际不符。
- **建议**：绑定 `config.RECOGNIZE_DAILY_LIMIT` 或直接用 `getAchievements` 返回的 `todayLimit`。

### 2.5 玩法配置双份维护

- **位置**：`miniprogram/config.js`（RARITY/LEVELS/RECOGNIZE_DAILY_LIMIT）与 `getAchievements/index.js`（LEVELS/BADGES）与 `recognizeFlower/index.js`（DAILY_LIMIT）各自一份。
- **问题**：改稀有度档位/等级阈值/每日限额需要改多处，易漏改导致前端展示与服务端计算不一致。
- **建议**：把玩法配置（等级阈值、徽章定义、限流值）收拢到云函数共享模块（如 `cloudfunctions/common/config.js` 通过 `require('../common/...')` 引入），前端保留展示用副本；或更彻底：新增只读配置集合 `app_config`，由 `getAchievements` 下发。

### 2.6 同卡照片数组无上限

- **位置**：`user_cards.photos` 无限 `push`；`saveCard` 不校验数量。
- **问题**：长期使用单卡照片可达数百张：单文档超 16MB 上限（照片仅存 fileID，体积小，但每张照片记录还有 metadata）、每次 `getCollection` 全量下发越来越大、删除性能下降。
- **建议**：限制单卡照片数（如 30 张），超限提示「已达上限，请删除旧照片」；或照片拆成独立集合 `card_photos`。

### 2.7 首页每次 onShow 双云函数请求

- **位置**：`pages/index/index.js` `onShow` → `loadData` 每次调用 `getCollection` + `getAchievements` 两个云函数。
- **问题**：tab 切回即刷新，无缓存无节流；云端调用量随使用线性增长（免费额度内可接受，但可优化）。
- **建议**：加「5 分钟内缓存」或 `onShow` 距上次刷新 <10s 时跳过；另外首页其实只需要 stats/level/recent，可让 `getAchievements` 直接返回 `recentCards`，合并成一个请求。

### 2.8 手动搜索依赖会话内 catalog 缓存

- **位置**：`pages/recognize/recognize.js` `getCatalog()`。
- **问题**：从分享链接直进识别页（或冷启动直接识别）时 `app.globalData.catalog` 为空，手动搜索退化为「仅当前候选中的已命中项」，搜索功能形同虚设。
- **建议**：catalog 为空时自动拉一次 `getCollection`（无参）补缓存，或改为服务端搜索接口（`searchSpecies` 云函数，防目录全量下发）。

### 2.9 `updateLocation` 与照片级 location/note 是死代码

- **位置**：`saveCard/index.js` `updateLocation` 分支、`makePhoto` 的 location/note；前端无任何调用。
- **问题**：需求规划了「地点」能力但前端未落地，接口空转；增加维护困惑（README 说「记录第 N 次遇见」，字段有 location 但 UI 无）。
- **建议**：二选一——补齐详情页「地点编辑」UI（v2 地域图鉴的前置），或从接口与文档中移除，避免误导。

## 三、🟡 低危：优化与加固（已全部修复）

### 3.1 每次识别全量拉取知识库

`getCatalog` 每次请求查 60 条 species（recognizeFlower/index.js）。建议云函数内做模块级内存缓存（`species` 变化频率极低，缓存 10 分钟 + 失败回退查库即可），显著减少冷链路耗时。

### 3.2 百度 Token 并发刷新风暴

`getBaiduToken` 无锁：并发请求同时发现 token 过期会同时刷新。无害但浪费；可在缓存过期时先 `set` 占位（新过期时间 30s）防并发，或用 `await` 队列。低优先。

### 3.3 相同照片重复识别无去重

用户对同一张照片反复「再次识别」会持续消耗限流并把同一张照片反复入 photos。建议前端记录最近一次上传的本地路径+时间（如 30s 内同一路径提示「这张刚识别过」），成本低体验提升明显。

### 3.4 无识别置信度阈值提示

百度返回低置信度（如 <60%）结果仍按普通候选展示，未提示「识别可能不准」。建议候选 `scoreText` 低时加提示文案，引导用户人工核对/手动搜索。

### 3.5 `rate_limits` 历史数据无限累积

每用户每天一条、无 TTL。建议云开发定时触发器（如每周）清理 30 天前的文档。

### 3.6 无主动监控与告警

云函数错误仅 `console.error`。建议：云开发控制台配置日志告警（如 recognizeFlower 错误率告警）；生产环境接微信订阅消息/群机器人通知。

### 3.7 低基础库兼容

`wx.chooseMedia` 需要较新基础库；`app.js` 只校验了 `wx.cloud`（2.2.3）。若想覆盖老设备，`chooseMedia` 失败时可降级 `wx.chooseImage`（compress 参数等价）。低优先，视目标用户设备分布决定。

### 3.8 无分享能力

未配置 `onShareAppMessage`。小程序默认不分享，会损失自然传播；至少首页应支持转发（文案用 config.SLOGAN）。个人主体无 UGC 风险，可放心开启。

### 3.9 识别页候选 wx:key

`recognize.wxml` 候选列表 `wx:key="name"`，若 Top3 中出现同名（百度偶发）会有渲染警告，改 `wx:key="index"` 或拼接唯一键。

### 3.10 云函数超时未显式配置

所有 `config.json` 只有 `permissions`，未配置 `timeout`。云函数默认超时较短（控制台默认 3 秒），而 `recognizeFlower` 链路含「下载图片 + 内容安全 + 百度 Token/识别 + 知识库查询」4 段网络调用，**极易超过默认超时**。建议在 `recognizeFlower` 的 `config.json` 显式配置 `"timeout": 20`，`saveCard` 等纯数据库操作可保持默认。

### 3.11 `baike` 展示的合规备注

### 3.10 `baike` 展示的合规备注

识别页对未收录候选展示百度百科摘要（`baike.description`），内容来自第三方。建议在展示区附带「百科信息来源于百度」署名，符合来源披露习惯。
